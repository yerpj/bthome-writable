bthome-writable — the whole round trip

Real bytes from a Puck.js on the bench. No acknowledgement channel: the refreshed advertising is the confirmation.

1 — Ordinary BTHome advertising
Three lights sharing one object ID, plus a declaration naming which positions are writable.
40 00 f0 01 64 1e 01 1e 01 1e 01 ff 1c
ff 1c = bitmask 0b00011100 → positions 2, 3, 4. Any BTHome receiver skips the unknown object; nothing else changes.
advertising
2 — Discovered, no configuration
The declaration says what to offer. Entities appear beside the sensors the core BTHome integration already made, on one device card.
4 — Applies it, and says so
Position addresses the instance — BTHome has no per-instance ID and this invents none. The next packet carries the new state.
40 00 f3 01 64 1e 01 1e 00 1e 01 ff 1c
one GATT write
3 — Writes every writable object, in packet order
Connect, write, disconnect. The object IDs are redundant given the position, and that is the point: they catch a receiver writing against a layout the device no longer has.
1e 01 1e 00 1e 01
1.7 s click → action → confirmation
0 extra bytes on the air for unencrypted devices beyond the 2-byte declaration
AES-CCM both directions, BTHome's own, when a bindkey is set
