Agreed on all three — and your same-packet rule is better than my list idea. You're right that objectIDs don't help with ten identical lights; "declaration + everything writable lives in one packet" solves rotation *and* multi-instance in a single move, because both the bitmask and the write order become positional within that packet. It also means a write is just the concatenated BTHome values in packet order, with the objectIDs acting as a sanity check. Two small things to pin down in the spec: the capacity limit becomes explicit (declaration + all writable objects ≤ one 31-byte payload — fine in practice, writable objects are few), and write-only objects need a no-op value so a write-all doesn't accidentally trigger them (length 0 = "don't modify" for text, and the existing BTHome "none" event value for button-like triggers — reusing BTHome's own semantics again).

On write-only: yes, and your corollary is exactly right — the device never advertises the written value, so on the HA side those become stateless entities (text/button style), outside the "advertising confirms the write" model. Cheap to handle.

On encryption: your 0x41 → 0xFF idea is precisely the right fix, and nicer than what I had in mind — the device-information byte is already part of the BTHome nonce, so flipping it for writes makes cross-direction replay cryptographically impossible with zero new fields. One caution on the "a write wouldn't include the 0xFF bitmask" argument though: that alone wouldn't have saved us, because a permissive write parser would skip the unknown 0xFF and still apply the rest of a replayed advertisement — so writes should strictly reject unexpected content anyway. And we still need one counter *per direction* (device tracks the last accepted write counter, separately from its own advertising counter), otherwise an old write can be replayed as a write. With the device-info split plus per-direction counters, replay is fully closed.

One implementation detail worth checking early: what the current `bthome-ble` parser does when it meets an unknown object ID like 0xFF. If it stops parsing, putting the declaration *last* in the service data keeps existing BTHome installs happy (sensors parse fine, declaration ignored); if it errors loudly, we'd start with the declaration in an Espruino manufacturer-data element instead (same payload, different container) until the ID is reserved.
